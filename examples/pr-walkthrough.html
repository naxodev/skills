Refresh before the first request

Moving one guard changes which credentials the server sees on the first request after expiry.

Illustrative example based on evals/fixtures/pr.json

1 · The settingThe request owned the refresh

The client already knew when its credentials expired. Its request function could compare that deadline with the current time and ask for a refresh. Both operations lived in the same function as the call that sent the payload. The missing piece was their order.

Before this change, the function sent the request, checked the expiry time, and then refreshed credentials when needed. That sequence placed maintenance after the operation that depended on it. The refresh could prepare the client for later work, but it could not change the credentials already used by the request.

2 · Why it mattersThe first request paid for the ordering

The fixture PR describes a specific failure: the first request after credential expiry failed. The client had the information and the refresh operation needed to avoid that failure, but it used them too late. A reader does not need a new authentication model to understand the bug. The request crossed the expiry boundary before its credentials were renewed.

That distinction matters because the change repairs the existing request path. It does not introduce a retry policy or a different credential store. The useful question is whether the request can reach the send operation before a required refresh has finished.

4 · The trade-offA check before dispatch

The PR body explicitly accepts an extra clock read to avoid the initial failed request. That is the author's stated cost. The supplied diff shows the check moving rather than a second check being added, so it does not independently establish an increase in clock reads. The visible change is where the existing check runs.

The source material records no rejected alternatives. It also provides no benchmark for the request path. The explanation can identify the accepted ordering and its purpose without turning either absence into an invented design debate or a numerical performance claim.

5 · The short versionOne ordering fixed, one path left to follow

The request function now refreshes expired credentials before sending the payload. The failure described in the PR came from doing those operations in the opposite order. Moving the guard makes the dependency explicit: the send operation waits for the credentials it needs.

Streaming requests remain on a separate path. The PR body names that path as follow-up work, and the supplied patch contains no streaming change. The next useful investigation is therefore the same ordering question in that path. This walkthrough makes no claim that the streaming behavior has already been fixed.
